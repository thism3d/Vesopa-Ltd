# Round two: the faults found on a real phone, an iPad and a Windows till

`PLAN-REDESIGN.md` covered building it. This covers what came back from using
it. Every item here is something the owner hit in a browser, in order, with a
screenshot.

Status: `[x]` done and proven on the live server · `[~]` partly · `[ ]` not started

---

## A — Identity: the two faults that lose an account

- [x] **A1 Microsoft sign-in fails.** The log said `AADSTS9002327`: the callback
      is registered in Azure under **Single-page application**, so the token
      endpoint only answers a request carrying a browser `Origin` header. The
      previous note said nothing in the codebase could work around it. That was
      wrong — an `Origin` header is a header, and a server can send one.
      `src/providers.js` now walks confidential → public → spa, remembers which
      one answered, and says what to change in the portal if none does. PKCE is
      sent in all three and is what actually protects a public client.
      `scripts/probe-microsoft.js` answers "which one will work?" with an
      invalid code, so this never again costs three real sign-ins to diagnose.

- [x] **A2 One address, one account.** Signing in with GitHub made an account
      holding `muzahid@onzep.uk`; typing the same address on the sign-in page
      made a SECOND account. Two causes, both fixed: GitHub was
      `trustsEmail: false`, so an address it had *verified* was thrown away
      (`profile()` already only reports `emailVerified` for a confirmed one);
      and nothing looked at a provider's asserted address when a code was
      proved. `user_identities.asserted_email_norm` (schema_012) plus
      `identity.findByAssertedEmail` closes it in both directions.

## B — The consent screen

- [x] **B1** Rebuilt to fit one phone screen: the account, the app, one line,
      the permission list COLLAPSED behind a tap, then Allow and Not now.
      `<details>`, so no script is involved.
- [x] **B2** The account chip is a control — it signs out and comes back to the
      same authorisation. A POST, because ending a session on a GET is
      something any page on the internet could do to you with an image tag.
- [x] **B3** An administrator of the application is warned, and switching
      becomes the primary action. A warning and not a refusal: looking at your
      own product's consent screen is a real thing to want to do.

## C — Access: not every app takes everybody

- [x] **C1** "Who can join" is stated at the top of the application's people
      page, in words, with a link to the switch that changes it.
- [x] **C2** Invite somebody from `/developers/a/<id>/people`, with a role, and
      see, re-send and withdraw what is outstanding. `invitations` has carried
      `application_id` since schema_002 and there was no way to make one, so
      "invited only" meant "nobody, ever".
- [x] **C3** Suspend and restore a member. Suspending revokes their refresh
      tokens, because otherwise "remove their access" means "in thirty days".
- [x] **C4** Being turned away is a page on this domain that names the
      application and the address, not a bounce to `error=access_denied` that
      arrives as "we could not finish signing you in".
- [x] **C5** `POST /api/app/invitations` — client credentials, confidential
      clients only — so an application can invite on a manager's behalf from
      its own screen. The back office uses it.

## D — The account area

- [x] **D1** Country and a per-kind device mark on Devices and Sign-in history,
      from `src/geo.js` (ported from `vesopa_hosting/src/geo.js`).
      `scripts/backfill-countries.js` fills in the rows written before it.
- [x] **D2** Date of birth is a real field. `input[type=date]` was not in the
      shared input rule at all, so Safari drew its own 102px pill.
- [x] **D3** The picture upload does something. `/js/profile.js` — the script
      the template's comment had always claimed existed.
- [x] **D4** "Getting back in" is its own panel with an Email/Phone toggle, and
      changing a recovery address goes through `/account/confirm` first.

## E — The shell

- [x] **E1** No browser loading bar: forms go through the router, and a
      redirect comes back as `204` + `X-Vesopa-Location` when the request says
      it came from there.
- [x] **E2** No blue box round the heading on iPad.
- [x] **E3** reCAPTCHA. Three separate faults, and the feature was inert:
      the `connect-src` violation; a missing token removing the password step,
      found by the smoke suite going red the day the keys were set; and — the
      one that mattered — the hidden field being rendered AFTER `</form>` on
      both pages, so no token was ever submitted at all. Every visible sign said
      it was working. `tool/auth_captcha_test.py` reads the POST body leaving a
      real browser, which is the only thing that settles it.

## Still open, and honest about it

**The Azure registration.** The `Origin` workaround means sign-in works without
touching the portal, and the portal is still where it should be fixed: put the
callback under **Web**, not **Single-page application**. Run
`node scripts/probe-microsoft.js` on the server to see which modes the
registration currently accepts.

**The shared password is public.** `github.com/thism3d/Vesopa-Ltd` is a public
repository and `vesopasoftware/server/seed.js` carried the admin and customer
password as a plain-text constant. It is out of the working tree and it is
still in the history, which is public too — so it must be treated as
compromised and **rotated**: the `vesopasoftware_authuser` database password,
the `info@vesopasoftware.com` login, and the mail accounts. No amount of code
fixes that.

**C2/C4 of the first plan** — the personal-info page is still one form rather
than a list of values opening editor pages, and the loading bar still starts on
a press rather than on first paint.
